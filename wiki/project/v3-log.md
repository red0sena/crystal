# v3 작업 기록 (2026-10-16~)

[위키 홈](../README.md) · [목표와 규칙](jev-index.md) · [전략](../designs/beat-d3-lite.md) · [2차 데이터](../designs/phase2-data-sources.md)

[목표](jev-index.md)를 위해 두 트랙을 병렬로 진행했다. **트랙 A**는 v3 모델 학습, **트랙 B**는 제출 전에 승패를 판단할 평가 기반이다. 아래는 실제 실행한 결과다. 진행 중인 항목은 따로 표시한다.

## 환경

- GPU: RTX A6000 48GB 1장. v3 전용 환경 `.venv-di`: torch 2.10 + cu128, transformers 5.17(d3-lite와 같은 버전), flash-linear-attention 0.5.2, decision-index 키트(`external/decision-index`, commit `f5a6e4f`).
- 모델: Qwen3.5-0.8B revision `2fc0636`(v1/v2와 같음), d3-lite 보드 측정 revision `a8d25a91`. 가중치는 v3.1.0과 main이 동일하고 런타임 코드만 다르다.
- **FLA 커널 검증** (`qwen_decision/v3/check_kernels.py`): FLA 0.5.2 backward가 일부 GPU/Triton 조합에서 틀린다는 보고(OneJev)가 있어 확인했다. 우리 환경은 Triton 3.6이다. 같은 입력을 FLA 경로와 PyTorch 기준 경로로 돌려 FP32 gradient를 비교했다. 코사인 ≈1.0000, 상대오차 약 1%(TF32 수준)로 정상이다. BF16에서는 상대오차가 최대 25%였는데, 이는 두 알고리즘의 반올림 차이다.
- 학습 두 개를 동시에 돌리면 각각 4~5배 느려졌다(CPU 바운드 커널 실행과 문맥 전환). 그래서 GPU 작업은 하나씩 순차로 돌린다.

## 트랙 B: 평가 기반

### 공개 suite 재구성과 검증

- `decision_index suite rebuild --edition 0.3`을 실행했다. HLE는 gated라 사용자 계정 승인이 필요했다.
- 보드에 공개된 d3-lite 결과 파일(`vllm-sr/d3-lite-decision-index`)의 `payload_sha256`과 run_id 단위로 대조했다. index 행은 HLE 501행을 포함해 모두 일치했다. 불일치는 RouterBench 10,000행과 SGD 2,500행인데 둘 다 **index에서 빠진** 벤치마크다(키트 빌더가 동결 이후 수정된 것으로 보인다).
- 이 두 벤치마크 때문에 키트가 0.2 cut과 GSM8K-v0.3 생성을 건너뛰어서, 키트 함수를 직접 호출해 마무리했다(`qwen_decision/v3/finish_suite.py`). 결과: 추가 벤치마크 7개·GSM8K-v0.3·제외 목록·채점 부분집합이 연구실 해시와 일치한다. 가져온 suite는 `external/decision-index/suite-0.3`에 있다.

### 공개 suite 샘플과 d3-lite 재현

- `qwen_decision/v3/board_check.py`로 벤치마크당 40그룹을 뽑았다. 2,149행, 37개 index 벤치마크 전부 포함이다(`runs/board/sample-40`).
- 키트의 `run`으로 d3-lite를 돌려 보드 결과와 대조했다. **필드 단위 결정 일치율 99.36%**(16,722 필드)로, 연구실의 재현 기준(BF16 98.5%)을 넘는다. 벤치마크별로는 ChessBench·POP909가 40문항 중 2문항씩 다르다(선택지가 많은 접전 문항).
- 키트 채점기로 같은 샘플을 채점한 공개 지수 추정치는 **우리 재현 39.65 / 보드 결과 39.56**이다. 샘플 추정치라 보드 공식값(36.93)과 다르다. 같은 샘플 위에서 모델끼리 비교하는 용도다.

### 비공개 대리셋: JEVal

- [JEVal](https://huggingface.co/datasets/carlosxiang/JEVal)은 58개 하위과제를 System One 형식으로 담고 있다. 출처당 60문항, 3,419문항을 쓴다(`qwen_decision/v3/proxy_eval.py`). index와 같은 역량인 22개 출처를 `same`, 나머지 36개를 `new`로 나눴다. **학습에는 절대 쓰지 않는다.**
- **엔진 검증:** 우리 엔진(`qwen_decision/v3/engine.py`)에 d3-lite 가중치를 넣어 d3 원본 런타임과 비교했다. 360문항에서 결정 일치율 98.6%, 정확도는 75.8% 대 75.6%다. 우리 프롬프트와 양방향 구현이 d3와 같다는 뜻이다. 이후 d3 체크포인트의 자체 `readout.safetensors`를 읽도록 하자 같은 360문항에서 **100% 일치**했다. 남았던 차이는 readout 행(임베딩 행 대 readout 파일) 때문이었다. d3-flash처럼 untied라 LM head가 없는 체크포인트도 이 경로로 읽는다.

### 오염 제거 필터

[`qwen_decision/v3/decontam.py`](../../qwen_decision/v3/decontam.py). 대상은 index 행 165,479개(0.1 원본 행이라 0.2에서 잘린 ToolRet 질의 7,704개 포함) + 추가 행 + GSM8K-v0.3 + JEVal 11,257개다.

- 13단어 shingle은 해시 기준 1/4만 남긴다. 3~30단어의 짧은 텍스트는 필드 전체와 줄 단위로 정확 일치를 본다. 숫자는 0으로 마스킹한다.
- index·JEVal에서 8행 넘게 반복되는 텍스트는 템플릿으로 보고 제외한다.
- 기본은 엄격 모드다. 문서 단위 분리를 따로 검증한 출처(ContractNLI)만 문서 모드를 쓴다. 선택지 텍스트는 shingle만 본다.
- 양성 대조 테스트(`decontam check`)를 통과했다. index 44개 벤치마크 표본과 JEVal 500개가 걸리고, 템플릿 안의 CLINC 발화도 잡히며, 무관한 문장은 통과한다.
- 한계: cfcolor·POP909처럼 반복되는 팔레트나 음표로만 된 문항과, 템플릿으로 생성된 CLadder·BBH 일부는 텍스트로 구별되지 않는다. 이 데이터셋들은 학습 출처에서 이름으로 제외한다.
- 이 필터를 다듬는 과정에서 RAGTruth의 90%가 템플릿 줄 때문에 오탐으로 버려졌다가 25%로 줄었다.

### 변형 ②: Jev 코퍼스만 (`runs/v3/v2-noncausal-d3`)

9.6만 행(Jev 1.13 soft label 8.2만 + Open-Jev 1.4만), 3,000스텝, lr 1e-5, noncausal + d3 프롬프트로 학습했다.

- 코퍼스 dev 교사 일치율은 38.1%→84.7%(KL 0.632→0.094), OOD는 67.2%→81.6%로 올랐다.
- **대리셋에서는 원본과 거의 같은 수준(0.241)이다.** 판정 형식은 배웠다. CLINC150 0.08→0.30, FEVER 0.43→0.77, HellaSwag 0.28→0.42다.
- 반면 **원래 지식을 잃었다.** ARC-Challenge 0.57→0.32, ARC-Easy 0.73→0.63, BoolQ 0.68→0.63, HaluEval-QA 0.87→0.73이다. 짧은 합성 시나리오만 담긴 코퍼스로 인한 망각이다(v2에서도 지식형 객관식 하락을 관찰했다).
- **공개 suite 샘플: 10.88점**(d3-lite 39.65, 같은 샘플). 실패 요청은 0건이고 순수 실력 차이다. 가장 크게 진 곳은 CLINC150 skill 0.00(d3-lite 0.80), BANKING77 0.12(0.89), HellaSwag 0.10(0.87), NLI4CT·VAST·CLadder 0.00(0.45~0.51), BFCL 0.32(0.84)다. 코퍼스는 최대 16지선다라, 무관한 선택지를 붙이는 패딩 증강만으로는 진짜 다지선다 변별을 배우지 못했다.
- 결론: 데이터 다양성 없이는 구조 비교도 의미가 약하다. 그래서 Jev 코퍼스만 쓰는 ①③④ 비교를 중단했다(①은 9스텝에서 중단, `runs/v3/aborted-v1-causal-d3-concurrent`). 혼합 데이터로 다시 비교한다.

### 원인 진단 (2026-10-16 저녁)

**장문 붕괴는 양방향 attention이 아니라 짧은 학습 데이터 때문이다.** 학습하지 않은 원본에 양방향만 켜서 JEVal 장문 과제를 쟀다(`runs/proxy/diag-base-noncausal-long`).

| 과제 | 원본 causal | 원본 + 양방향 (학습 없음) | ② 혼합 (학습 후) | d3-lite |
|---|---|---|---|---|
| LongBench 검색 en | 0.47 | 0.40 | 0.27 | 0.97 |
| LongBench 검색 en-e | 0.80 | 0.82 | 0.48 | 1.00 |
| LongBench 검색 zh | 0.42 | 0.33 | 0.42 | 0.98 |
| LongBench LSHT | 0.42 | 0.52 | 0.45 | 0.53 |
| HELMET | 0.15 | 0.12 | 0.08 | 1.00 |

양방향 전환만으로는 거의 변화가 없고, 짧은 판정 데이터로 학습한 뒤에 떨어진다. d3-lite가 원본보다 훨씬 높은 것은 장문 과제를 학습했다는 뜻이다. 처방은 `long-context` 출처다. ProLong(Gao et al., ACL 2025)도 장문 능력을 지키려면 학습에 장문과 단문을 섞고, 평가 길이 이상으로 학습하라고 권한다.

**학습 속도 정정:** "양방향 학습이 2.4배 느리다"는 판단은 틀렸다. ①과 ②는 배치가 같으니 같은 스텝끼리 비교했더니 속도 비율이 1.0~1.16이다. 원래 판단은 짧은 배치 한 스텝의 값을 잘못 읽은 것이다. attention 연산만 떼어 보면 padding mask SDPA가 causal flash보다 5.6배(1천 토큰)~8.4배(4천 토큰) 느리다. 하지만 softmax attention은 24층 중 6층뿐이다. 패딩을 빼고 묶는 `varlen_attn` 커널을 `modeling.VARLEN`으로 구현했고, 모델 전체로는 약 18% 빨라졌다. 결과 차이는 BF16 수준이다(logit 0.125, gradient 코사인 0.9988). 구조 비교의 일관성을 위해 기본값은 mask 방식(sdpa)으로 두고, varlen은 본 학습에서 쓴다.

**지식 망각:** full fine-tune은 LoRA보다 원래 능력을 더 잃는다(Biderman et al. 2024, "LoRA Learns Less and Forgets Less"). 가중치 보간(WiSE-FT, Wortsman et al. 2022)은 추가 학습 없이 분포 밖 성능을 회복시키는 방법이다. 둘 다 이후 실험 후보다.

### 구조 비교 중단과 학습 속도 개선 (2026-10-16 밤)

**구조 비교 중단:** ①(causal)과 ②(양방향)는 같은 500스텝에서 dev 0.69/0.66, ood 0.72/0.75로 거의 같았다. 구조는 핵심 변수가 아니라고 보고 ②(d3-lite와 같은 구조)로 정했다. ③④와 ① 나머지 학습은 취소했다.

**학습 속도:** torch profiler로 한 스텝을 쪼개 보니 행렬곱은 24%뿐이었다. 원인과 처방은 다음과 같다(같은 배치 기준).

| 원인 | 비중 | 처방 (`modeling.py`, `train.py`) |
|---|---|---|
| FP32 가중치 + BF16 autocast: residual이 FP32로 흐르며 층마다 변환·복사 | 24% | BF16로 계산하고 FP32 master 가중치·모멘트는 옵티마이저에만 둔다(`MasterAdamW`) |
| `causal-conv1d` 미설치로 DeltaNet conv가 FP32 PyTorch 대체 구현 | 15% | FLA Triton conv(`fla_causal_conv1d`). FP32에서 출력·gradient 동일 |
| 패딩 토큰 | 34% | 패딩 없이 이어 붙이기(`packed_hidden`, cu_seqlens를 varlen attention·FLA scan·FLA conv에 전달). 행 사이 누출 없음을 확인했다 |
| FLA conv가 토큰 수 구간마다 재컴파일·재튜닝(`NB=cdiv(B*T,1024)`가 constexpr, 커널 본문은 안 씀) | 이어 붙이기 시 23초/스텝 | `_FixedNB`로 NB 고정. 이후 재컴파일 0회 |
| 합쳐지지 않은 원소별 연산(RMSNorm, gated norm, SwiGLU) | 35% | 해당 블록만 `torch.compile(dynamic=True)`(`compile_elementwise`). 동일 입력에서 eager와 FP32 1e-6 일치 |
| gradient checkpointing 재계산 | 약 25% | 8천 토큰 이하 microbatch는 체크포인팅을 끈다(`--checkpoint-above`) |
| microbatch마다 `.item()` 동기화 | 소량 | 스텝당 한 번만 읽는다 |

결과: ②의 실제 학습은 5.6초/스텝(2,000스텝 3시간 12분)이었다. 같은 설정의 새 경로는 1.19초/스텝이다(train.py 종단 시험, 메모리 최대 24GB, 첫 스텝에 1회 컴파일 약 90초). 같은 배치 비교로도 약 3배 빠르다. 결과 차이는 BF16 수준이다(packed vs padded gradient 코사인 FP32 0.9999, BF16 0.997). 학습된 체크포인트는 기존 엔진에서 그대로 읽힌다.

### 정답 전용 학습으로 정비 (2026-10-17, 검토 피드백 반영)

방침: **교사 모델에게서는 아무것도 배우지 않는다.** 학습·개발·모델 선택 모두 교사 유래 데이터를 쓰지 않는다. 위 "정답 학습" 항목(yuri argmax를 정답으로 쓰던 방식)은 이 방침으로 대체했다.

- **데이터(`mix.py`, `data/mix/v3-gold.jsonl`):**
  - `yuri_v3`는 읽지 않는다. 코퍼스 README상 Jev 1.13에서 증류한 라벨이다.
  - `openjev_v2`는 구성별 라벨 출처를 확인하기 전까지 뺀다. Open-Jev 카드는 참조 라벨이라고 하지만, 일부 구성은 judge와 teacher/control 라벨을 언급한다.
  - `apibank-train`은 재구성을 검증하기 전까지 뺀다. 선택지의 84.7%가 입력에 없었다. 재구성 작업은 중단됐고 산출물은 검증되지 않았다.
  - 결과: 20만 문항, 41개 출처. 비율은 장문 12%, 나머지 공개 train 88%다. (2차 검토에서 38개 출처로 바뀜)
- **라벨 필드 분리:**
  - `label_origin`(누가 정답을 정했나)은 human / programmatic / model이다. model은 ToolACE·Glaive·When2Call처럼 생성 파이프라인이 만든 공개 데이터셋이다.
  - `target_kind`(정답 형태)는 single / valid_set / vote_distribution이다. Habermas 공동 1위는 valid_set이고 어느 것이든 정답이다. VAST 주석자 불일치는 vote_distribution이고 다수 의견이 정답이다.
  - 학습 목표는 `train.gold_targets`가 정답에서만 만든다.
- **정답 개발셋(`v3-gold.dev.jsonl`, 6,247문항, 출처마다 140문항 이상):**
  - 샘플링 전에 같은 문서 그룹 단위로 떼어 둔다(`mix.data_groups`).
  - 같은 문서란 작은 쪽 정규화 문단의 절반 이상을 공유하는 것이다. 출처가 달라도 묶는다.
  - 50행 넘게 반복되는 문단(템플릿, 도구 스키마, 라이선스)은 판단에서 뺀다.
  - 문단 하나만 겹쳐도 묶었더니 2.3만 행짜리 연쇄 그룹이 생겨 기준을 바꿨다.
  - 검증: ECtHR a/b의 같은 사건 8,946건이 모두 한 그룹이고, CUAD 계약서와 QuALITY 글은 하나도 쪼개지지 않았다.
  - 빌더가 원본 문서 id를 남기지 않아서 내용 연결로 대신했다. 원본 id를 기록하도록 빌더를 고치는 일은 남아 있다.
- **모델 선택과 export(`train.py`):**
  - 정답 개발셋의 출처별 정확도 평균으로 고른다. 정답 개발셋이 없으면 오류로 멈춘다.
  - 코퍼스 dev/ood(교사 라벨) 평가는 학습 루프에서 뺐다.
  - `best/`와 `last/`를 모두 export하고, `final`은 best를 가리킨다.
  - `--steps`로 업데이트 수를 데이터 양과 따로 고정한다. 한 바퀴를 넘으면 매번 다시 섞어 반복한다. 처리한 문항·토큰·업데이트·바퀴 수를 기록한다.
- **JEVal 프로토콜(`runs/proxy/protocol/jeval-v2.json`):**
  - 51개 출처를 문서 그룹 단위로 dev 4,928문항과 restricted 4,929문항으로 나눴다.
  - restricted는 **지금부터 접근을 제한하는 부분집합**이고 깨끗한 봉인 시험이 아니다. 지금까지 JEVal 결과가 이미 설계에 영향을 줬다.
  - 진짜 최종 시험은 보드의 비공개 시험이다.
- **회귀 검사(`python -m qwen_decision.v3.check_packed`, 실패 시 종료 코드 1):** FLA conv, compile 블록, packed/padded logits·gradient, 행 독립성 7개 항목이 통과했다. 사전 검사는 `passed: false`면 종료한다. 학습 셋 전체에서 가장 긴 문항(61,102토큰, 20.7GB)도 확인한다.
- **compile 수정:** 메서드를 compile하면 모듈 인스턴스마다 재컴파일돼 한도(8)에 걸렸다. 텐서 함수로 바꾸고 입력을 2차원으로 폈다.
- **환경 고정:** `requirements-v3.lock`(.venv-di: torch 2.10.0+cu128, transformers 5.17.0, fla 0.5.2, triton 3.6.0). 루트 `pyproject.toml`(transformers 5.18)은 v2 환경이다.
- **정정:** "장문 붕괴는 짧은 데이터 때문"은 가설로 낮춘다. ProLong은 장문 continued training 뒤의 짧은 SFT를 다룬 연구라 근거로 맞지 않는다. 구조와 미세조정의 상호작용도 배제되지 않았다.

### 2차 검토 반영 (2026-10-17)

앞 항목의 "정비 완료"는 이르다는 검토가 있었고, 데이터로 확인하니 맞았다.

- **모델이 만든 정답 제외:**
  - ToolACE·Glaive(`tools-percall`)와 When2Call은 생성 모델 파이프라인이 정답을 만든 데이터다. When2Call 저장소에는 Mixtral 합성이라고 명시돼 있다.
  - `phishing`의 LLMGen 행도 GPT가 쓴 이메일이다.
  - 그래서 `label_origin=model`로 분류했고, 학습 셋과 학습 모두 기본값에서 뺀다(4.5만 행).
  - 그 결과 **도구 영역 데이터가 비었다.** API-Bank 재구성 검증이 끝나야 채워진다.
- **실제 누수 확인과 수정:**
  - 개발셋에 원본 항목 단위 누수가 있었다. MuSiQue 7개(예: `2hop__729631_64008`의 answerable 버전은 학습, unanswerable 버전은 개발), tools-percall 11개, When2Call 1개(`pref:5515` 2지선다/4지선다)였다.
  - 이제 모든 출처를 `mix.SOURCES`에 (label_origin, 행 id에서 원본 항목 키를 뽑는 함수)로 등록한다. 같은 항목 키는 한 그룹이다(ECtHR a/b는 같은 사건 키).
  - 미등록 출처는 오류다. 이전에는 `human`으로 자동 분류됐다.
  - 개발셋과 학습 셋에 같은 항목 키가 있으면 빌드가 실패한다. 독립 재검사 결과도 0건이다.
- **분할 반례 수정:** 짧은 문단만 행 수(50) 상한으로 템플릿 판정을 했더니, 같은 지문에 질문이 51개면 51그룹으로 쪼개졌다.
  - 이제 문단 전체를 긴 조각으로도 넣는다(200자 이상, 1,000행 이하).
  - 시험 결과: 50·51·300개 질문은 한 그룹이고, 1,200개는 라이선스 문구 상한에 걸리는 한계로 남는다.
- **업데이트 수 보장:** `--steps`는 실제 optimizer 업데이트 수다. 빈 배치는 세지 않고 기록한다. 업데이트가 부족하면 오류로 멈춘다.
- **개발셋 전체 사용:** 모델 선택은 개발셋 전체(5,814문항, 38개 출처)로 한다. 이전에는 출처마다 파일 앞부분 100개만 썼다. 표본을 쓸 때는 id 해시로 고정한다. 평가 한 번에 약 74초가 걸린다.
- **현재 학습 셋 v3-gold:** 20만 문항, 38개 출처, human 92% / programmatic 8%. JEVal 프로토콜 v2는 이 그룹 규칙으로 다시 만들었다(dev 4,931 / restricted 4,926).

### 학습 속도 검토 반영 (2026-10-17, `bench_train.py`)

같은 고정 배치(v3-gold 앞부분, 32문항 × 측정 24스텝, 문항당 평균 1.2천 토큰)에서 단계마다 device 동기화로 끊어 쟀다. `train.py`의 `step_seconds`는 렌더링 포함, 동기화 후 값으로 바꿨다.

| 설정 | 준비 | forward+backward | 옵티마이저 | 스텝 | tokens/s | 최대 메모리 |
|---|---|---|---|---|---|---|
| 이전 경로 (GPU packing, K/V 복제), budget 8k / ckpt 8k | 47ms | 2.216s | 86ms | 2.352s | 14,517 | 24.1GB |
| CPU packing + native GQA + foreach, 8k / 8k | 48ms | 2.202s | 85ms | 2.337s | 14,565 | 26.9GB |
| 16k / ckpt 8k | | 2.483s | | 2.610s | 12,706 | 26.7GB |
| **16k / ckpt 16k** (foreach 끔, 새 기본값) | 48ms | 2.043s | 86ms | **2.174s** | **15,548** | 36.3GB |
| 32k / ckpt 16k | | 2.417s | | 2.546s | 13,082 | 38.9GB |
| 32k / ckpt 32k | | | | | 메모리 부족 | |

- **native GQA:** `varlen_attn`이 K/V 2헤드와 Q 8헤드를 바로 받는다. 출력은 같고 attention 연산만 약 3% 빨랐다.
- **CPU packing(`modeling.pack_rows`):** GPU 경로와 logits가 완전히 같다(차이 0). 동기화 지점(boolean index, `.any()`, `int(max)`, `torch.unique`)이 없어지고 FLA에 `cu_seqlens_cpu`를 넘긴다.
- **결론:** 위 두 개와 foreach 복사를 합쳐도 스텝 단축은 0.6%다. 스텝의 94%가 forward/backward 계산이다.

### d3-lite 구조·가중치 감사 (외부 검토, `runs/analysis/d3-lite-structure-audit.json`)

d3-lite의 백본 텐서 473개를 원본 Qwen(revision 2fc0636)과 원소 단위로 비교했다(forward 없음).

- 구조: 24층(Gated DeltaNet 3층 + full attention 1층 × 6), 은닉 1,024. full attention 6층만 양방향, 마지막 입력 토큰 은닉 상태 × 별도 readout(255×1024, FP32) → 표시된 선택지끼리 softmax(T=1). 우리 엔진의 재현과 같다(360문항 100% 일치).
- 입력 임베딩: 원소의 67%가 원본과 다르고 상대 L2 변화 1.05%. **임베딩을 동결했다는 앞선 추정(readout 행과 원본 임베딩의 코사인 0.99995에서 추론)은 틀렸다.** 24층 모두 변했다. 마지막 정규화는 원본과 같다. 비전 153텐서 중 148개는 원본과 같고 바뀐 것은 주로 merger다.
- readout: 원본 LM head 코드 행과 코사인 0.99994, 상대 L2 1.1%. d3 자신의 입력 임베딩 같은 행과는 1.8% 차이로, 같은 행렬이 아니다.
- 이 결과로 full fine-tune과 LoRA 병합은 구분되지 않는다. 학습 데이터·손실·스텝도 가중치로는 알 수 없다.

### 가중치 이동량: d3-lite 대 g1 (`qwen_decision/v3/weight_drift.py`)

원본 Qwen 대비 상대 L2 변화(‖w−원본‖/‖원본‖). 구조 감사 원자료는 `runs/analysis/d3-lite-structure-audit.json`.

### 코드 배정 증강 복원 (2026-10-17, g1 이후)

g1은 선택지 내용 순서만 섞고 코드는 항상 위에서부터 A, B, C…였다(위치와 코드가 묶임). v2 계획(`docs/v2_plan_ko.md` B)의 배정을 `train.Renderer`에 되살렸다. 순서 없는 choice 문항(noul을 choice로 보인 문항 포함)에만 적용한다.

- 약 60%: 표시 순서대로 A, B, C… (추론 형식).
- 20% (`--code-shuffle-probability`): 앞 k개 코드를 섞어 배정.
- 20% (`--code-sample-probability`): 255개 중 k개를 뽑아 코드 순서대로 배정. 짧은 목록에서도 모든 코드가 정답이 될 수 있다.
- 검증: 4,000문항을 렌더링해 정답 코드 줄의 내용이 원래 정답 내용과 모두 일치(불일치 0). 배정 비율 58/21/20%.
- 근거와 한계: v2 보고서에서는 코드 형식을 바꿔 다시 채점해도 1%p 안쪽 변화였고 위치 편향도 관찰되지 않았다. 효과가 클 것이라는 근거는 없고, 같은 조건 비교로만 판단한다. g1 재현은 두 확률을 0으로.

### 외부 검토(alphaXiv 10편 대조) 반영 (2026-10-17)

- **선택지끼리 위치로 참조하는 문항:** "both B and C", "None of the above", CaseHOLD의 "(a)" 라벨처럼 섞으면 의미가 바뀌는 문항이 v3-gold에 1,235행 있다(lexglue-short 966, medmcqa 192, aqua-rat 36, mmlu-aux 23 등). `mix.positional_options`가 감지하고, `train.Renderer`는 이런 문항에서 내용 순서·코드 배정·패딩을 모두 끈다. 기존 mix를 다시 만들 필요 없이 렌더링 시점에 적용된다. 전체의 0.6%라 격차 설명력은 작지만 틀린 학습 신호다.
- **학습 표본 진단(`--train-probe-per-source 25`):** 소스별 고정 학습 25행을 증강 없이 매 평가 때 채점해 eval.json의 `train_probe`에 기록한다. 학습 표본도 틀리면 미학습, 학습 표본은 맞히고 dev에서 틀리면 일반화 문제다. 모델 선택에는 쓰지 않는다.
- 보류: 순열 일관성 손실(추가 forward 비용, 우선 orders=4 평가로 뒤집힘 비율부터 측정), 패딩 제거 비교, 학습률 3점 비교, 영역별 배분, readout 분리(d3 readout은 원본에서 1.1%만 이동해 우선순위 낮음).
- **순서 편향 측정(`qwen_decision/v3/bias_eval.py`):** JEVal choice 문항을 4가지 표시 순서로 채점해 답 뒤집힘 비율(flip_rate)과 위치별 정답 재현율의 표준편차(RStd), 첫 위치 선택률을 따로 낸다(Ok et al. 2026의 두 요인 분리). g1·g1-wise50·d3-lite를 측정한 뒤 일관성 손실 도입 여부를 정한다.
- **학습률:** 검토안의 3e-6/1e-5/3e-5 중 3e-6만 먼저 돌린다(g2). 이동량과 WiSE 결과가 모두 과도한 변화를 가리키므로 3e-5와 2바퀴는 지금은 반대 방향이다.

### 망각 완화 도구 (2026-10-17, 외부 조사 반영)

- **L2-SP 앵커(`train.py --anchor`, `MasterAdamW`):** AdamW의 0 방향 weight decay 대신 매 스텝 가중치를 원본 쪽으로 `lr × anchor`만큼 당긴다(분리형 L2-SP, Li et al. 2018). 손실에 벌점을 더하면 Adam이 좌표별로 다시 스케일하므로 분리형으로 구현했다. 표류의 기억 길이는 약 1/(lr·anchor) 스텝(lr 1e-5, anchor 100이면 약 1,000스텝). 원본 사본에 FP32 약 3GB. 단위 시험: 기울기 0에서 +1 표류가 lr·anchor=0.1만큼 줄어 0.9가 된다. 기본값 0(꺼짐, 기존과 동일).
- **문항별 망각 보고(`qwen_decision/v3/forget_report.py`):** 같은 JEVal 행에서 원본(같은 noncausal·d3 프롬프트) 대비 맞힘→틀림, 틀림→맞힘을 소스별로 센다. 정확도 하나로는 "덜 배우고 덜 잊음"과 "더 배움"이 구별되지 않는다.
- 미적용: 보존용 정답 재노출(현재 mix가 이미 지식·추론 소스를 섞고 있어 비율 조정 실험으로 다룬다), MoFO(텐서별 top-k가 매 스텝 비용, 구현 후 속도 측정 필요), FINCH(선택지 수에 따라 손실 크기가 달라 그대로 쓰기 어려움), 원본 출력 KL(교사 학습 금지 방침).

- **phishing dev 0행 버그:** 항목 키가 파일:라벨이라(`_after(3)`) 7,075통이 3개 항목으로 묶여 dev에 한 번도 뽑히지 않았다(g1 mix도 동일). 키를 파일:라벨:본문 해시(`_after(4)`)로 고쳐 v3-gold·v3-gold2를 다시 만들었다. 이제 모든 학습 소스에 dev가 있다(phishing 150). v3-gold2: 199,981행, dev 6,719행.
- **해석 정정:** 망각 보고의 "덜 배운 몫 212 대 더 잊은 몫 77"은 d3-lite가 새로 맞힌 문항이 더 많다는 뜻이지, 학습 횟수가 부족했다는 증거가 아니다. 데이터 구성이나 학습 방식도 원인일 수 있고, 3에폭 실행은 그중 학습량 가설을 확인하는 실험이다. 또 3에폭 실행의 epoch-1은 독립된 1에폭 학습과 다르다(warmup과 cosine 일정이 전체 스텝 기준).
- **g3 설정과 평가:** 3에폭, lr 3e-6, anchor 0 — "anchor 없이 낮은 학습률로 오래 학습"하는 비교 실험으로 기록한다. 평가 대상은 각 에폭 끝 모델에 더해, gold dev가 에폭 끝이 아닌 스텝을 골랐으면 `final/`(=best)도 포함한다.

### dev 분할 규칙 개정 (2026-10-18, `mix.hold_out`)

웹 검색한 관행에 맞춰 dev를 다시 만들었다.
- 크기는 감지하려는 차이로 정한다(검정력).
- 그룹 단위 분할(GroupShuffleSplit)을 쓴다.
- 분할 전에 근사 중복을 제거한다.
- 겹침 0을 단언한다.
- dev는 목표 분포를 반영해야 한다.

- **크기**: 출처당 min(300, 그 출처 행의 10%).
  - 같은 문항으로 체크포인트를 짝지어 비교하면, 300문항은 출처 정확도 약 5점 변화를 검정력 80%로 감지한다(불일치 문항 약 12% 가정). 매크로(약 50개 출처)는 약 0.7점이다.
  - 150문항일 때 출처별 오차는 ±3.1점, 300문항이면 ±2.2점이다.
  - 작은 출처는 10%까지만 가져간다. 예: PubMedQA 150→100.
- **표본 추출**: 무작위 행을 고르고 그 행의 그룹 전체를 dev에 넣는다(행 비례).
  - 이전 방식은 그룹을 균등하게 뽑았고 50행 넘는 그룹은 아예 뺐다. 그래서 큰 문서의 문항이 dev에 빠지는 쏠림이 있었다.
  - 이제 상한은 목표의 절반이다.
- **API-Bank**: API 카탈로그 문단이 행을 연쇄로 묶어 66%가 1,000행 넘는 한 그룹이었다. 내용 연결에서 빼고 항목 키(대화)와 근사 중복으로만 묶는다(`CONTENT_LINK_EXEMPT`).
  - dev 300행 중 희귀 8-gram이 80% 이상 겹치는 학습 행이 있는 것은 1행이다.
- **결과 (v3-gold3)**:
  - dev 15,154행(3.7%). 모든 출처가 목표의 90% 이상을 채웠다.
  - dev 대상이 될 수 있는 행 비율이 80% 미만인 출처: MuSiQue 0.49, When2Call 0.67, SQuAD2 0.73(큰 문서 그룹). 이 셋은 dev 대표성이 제한된다.
- v3-gold·v3-gold2는 예전 규칙으로 만든 파일 그대로 둔다(g1·g3 재현용).
- 평가 시간: dev 1.5만 + 학습 표본 1,275행이라 중간 평가 한 번에 약 8분이다.

### 섞기 모델 정리 (2026-10-19)
