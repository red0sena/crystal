# 내부 블록 반복: 실제 계산 구조 변경

가중치 평균 대신 g4b의 Transformer 내부 실행 경로를 바꾼다. 첫 20개 층을 거친 뒤, 17–20번째 층(0 기반 `[16:20]`, DeltaNet 3개 + full attention 1개)을 같은 가중치로 한 번 더 실행하고 나머지 4개 층으로 보낸다. 실효 깊이는 24층에서 28층으로 늘어난다.

추가 경로의 출력은 `h + tanh(g) * (Block(h) - h)`다. `g`는 1,024개 FP32 채널이며 0으로 초기화한다. 초기 출력은 원본과 정확히 같고, 학습으로 반복 계산을 얼마나 반영할지 정한다. LM head, 프롬프트, 코드 체계는 그대로 사용한다. 여러 모델의 가중치나 예측을 평균하지 않는다.

[Recurrent Depth 연구](https://www.alphaxiv.org/abs/2502.05171)는 공유 블록을 반복하는 설계의 근거다. 해당 논문은 대규모 사전학습을 포함한다. 여기서는 기존 Decision 체크포인트에 유한한 추가 패스를 붙여 적응 학습한다. 원 논문의 재현이나 성능 보장은 아니다.

실험은 `runs/recurrent/internal4-v1/plan.json`에 먼저 고정한다. 동일 g4b 가중치에서 기본 구조와 반복 구조를 출발시키고, 동일 정답 데이터·선택지/코드 순열·512 업데이트·배치 16·학습률을 사용해 언어 백본과 tied embedding/head 전체를 학습한다. 새 게이트만 별도 학습률을 쓴다. 반복 구조의 연산량이 더 많으므로 동일 FLOPs 비교라고 부르지 않는다.

gold6 dev에서 전체 gold2/3/6 학습 데이터와 이전 gold3 dev·fresh-v1/v2·JEVal의 공유 문서/입력 그룹을 제외했다. 새 selection에서 각 실험의 step 0/256/512 중 하나를 독립적으로 선택하고, 두 체크포인트를 고정한 뒤 분리한 confirmation을 한 번 비교했다. 출처별 정확도 평균과 문서 단위 paired bootstrap 95% 구간을 보고한다. 근사 의미 중복까지 제거했다는 뜻은 아니다.

구현은 [recurrent.py](../../qwen_decision/v3/recurrent.py), 실험은 [recurrent_experiment.py](../../qwen_decision/v3/recurrent_experiment.py)에 있다. 저장된 체크포인트는 `recurrent.load(path)` 또는 기존 `engine.Scorer`로 읽는다. 일반 Transformers 로더만 쓰면 추가 실행 경로가 생략된다.

## 측정 결과 (2026-10-19)

**구조 변경·전체 백본 학습·확인셋 평가를 완료했지만, 추가 구조의 정확도 개선은 확인되지 않았다.** seed 41의 한 번의 비교다. 신뢰구간은 이 두 학습된 체크포인트와 출처 구성에서 문서를 재표집한 것이며, 학습 seed 변동까지 포함하지 않는다.

학습 풀은 12,290문항/100출처이며, 두 구조 모두 같은 순서의 8,192개 표본을 512 update·배치16으로 읽었다. 매 스텝 입력 token hash의 불일치는 0개였다. 언어 백본과 tied embedding/head 752,393,024개 파라미터를 양쪽 모두 학습했고, 반복 구조에는 게이트 1,024개가 추가된다. 기존 정답 정책을 따랐고 새 teacher label이나 rationale는 만들지 않았다.

선택셋은 **4,147문항/77출처/1,758문서 그룹**이다. 기본 구조의 step 0/256/512 정확도는 **71.43/73.94/75.74%**, 반복 구조는 **71.43/73.82/75.60%**였다. 양쪽 모두 step512가 선택됐다. 초기 4,147문항에서 두 구조의 예측과 확률은 정확히 일치했다.

동결한 확인셋은 **8,823문항/77출처/4,413문서 그룹**이다. 두 체크포인트와 구조 파일의 hash를 확인셋 추론 전에 고정했다.

| 구조 | 확인셋 출처 평균 정확도 | 같은 8,823 prompt의 추론 시간 |
|---|---:|---:|
| 기본 구조, 같은 추가 학습 | 75.20% | 143.39초 |
| 중간 4블록을 추가 반복 | 75.29% | 165.29초 |

차이는 **+0.10%p**, 출처를 유지한 문서 bootstrap 5,000회 95% 구간은 **[−0.20,+0.45]%p**다. 40문항을 회복하고 35문항을 악화시켰다. 추론은 같은 3,645,308개 입력 token·같은 SDPA·배치 예산으로 측정했으며 모델 로딩과 tokenization은 제외한다. 반복 구조가 **15.27%** 느렸다. 정확도 차이가 불확실한 데 비해 추가 연산 비용이 있어 이번 결과로 반복 구조를 기본값으로 채택하지 않는다.

학습·선택셋 측정·저장을 합친 시간은 기본 **873.19초**, 반복 **1,023.80초**였다. 최대 CUDA allocated memory는 각각 **13.89/13.90GB**였다. 추가 계산이 있는 구조이므로 동일 FLOPs 비교는 아니다. 두 저장 모델 모두 전체 선택셋 재로딩 예측 불일치가 0개였다.

추가 학습 전 원래 g4b의 같은 확인셋 정확도는 **71.67%**였다. 기본 구조도 동일한 추가 학습으로 **75.20%**가 됐으므로, 반복 구조가 원래 g4b보다 높은 차이 전체를 구조 변경의 효과로 해석하면 안 된다.

기존 `Scorer` API의 128문항 검증에서는 전용 로더와 예측 불일치 **0개**, 최대 확률 차이 **1.89e-7**이었다. 33개 배치에 text forward가 각각 한 번 발생했고, 그 안의 Transformer 블록 실행 수는 매번 **28개**였다. 게이트는 1,024채널 모두 0이 아니었으며 RMS **0.01006**, 범위 **[−0.03824,+0.02853]**였다. 이 표본에서 추가 경로가 BF16 표현을 바꾼 비율은 53.10%, 입력 표현에 대한 변화의 norm 비율은 0.367%였다. 추가 경로의 실제 작동을 확인한 것이며 정확도 개선을 증명하는 수치는 아니다.

초기 출력 일치·공유 파라미터·체크포인팅 역전파·혼합 attention 패딩·새 인스턴스 재로딩을 다루는 테스트 4개, 변경 Python 모듈의 컴파일 검사, diff whitespace 검사를 통과했다. 모든 학습/평가 프로세스의 종료와 GPU 유휴 상태를 확인했다.

반복 구조의 실제 체크포인트는 `runs/recurrent/internal4-v1/recurrent/step-512/`에 남겼다. 기존 `engine.Scorer`가 `decision_architecture.json`을 감지해 새 계산 경로를 복원한다. 기본 Transformers 로더만 쓰면 추가 경로가 생략되므로 이 저장 모델은 저장된 구조 파일과 전용 로더가 함께 필요하다.

원문 문항·예측·확률·학습 log·모델·동결 source는 `runs/recurrent/internal4-v1/`에 있다. 준비 단계의 추가 JEVal 교차 검사에서 선택용 15개·확인용 29개 문서 그룹을 제외했으며, 채워 넣지 않고 최종 입력 파일과 hash를 고정했다. 이 보정은 모델 선택/확인 추론 전에 끝났고, 앞선 파일도 `*-before-jeval-audit.jsonl`로 보존했다. 재실행할 때는 이 동결된 입력을 사용해야 같은 비교가 된다.

최종 수치와 검증 기록은 [결과 JSON](recurrent-depth-results.json)에 정리했다. 이 확인셋은 이제 관찰했으므로 새 구조를 고르는 데이터로 재사용하지 않는다.
